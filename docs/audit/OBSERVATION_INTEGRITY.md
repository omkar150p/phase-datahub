## Recommended additions

1. **Add structured occurrences and wire offsets.** Introduce a small additive table, provisionally `consensus_view_observations`. Use `(response_id, response_index)` as the primary key and a composite `(source_id, response_id)` foreign key to `rpc_responses`. `response_index` is the original zero-based index in the JSON-RPC `result` array, assigned before sorting or deduplication. Index `(source_id, view_id, response_id, response_index)`. Store the lossless view ID, source-reported timestamp, status, block hash, epoch, round and normalized record with ordered members/signers. Read the source, receipt time, ingestion time and original bytes through the parent response. Mark the normalizer version independently of the original receipt time.
2. **Keep one representative projection.** Preserve existing certificate precedence and tie behavior. For new writes, record the selected occurrence offset only when that occurrence supplied the displayed record. Existing response pointers can continue to work where a unique offset cannot be established. Store variants separately. A different signer list never causes the archive to lose another observation.
3. **Capture all committed view-method occurrences.** Include normal pages, retention probes and superseded polls. These observations are evidence even when the poll could not update the projection or a view lay beyond the repair cursor. Keep the raw body, occurrence insert and normal checkpoint update transactional. Backfill from the losslessly parsed archived bodies in bounded, restartable batches. Use the response and index key on replay and verify equality on a reprocessed key. Record parse failures for review and leave the original payload accessible. Historical backfill must leave projection and checkpoint state intact.
4. **Add scoped findings.** Compare only within a source and view. Require the same epoch, round and comparable committee/leader context for signer membership comparisons. Keep the order and multiplicity of the original lists for inspection, and use normalized set comparison to distinguish membership changes from permutations. Compare distinct fact signatures, so repeated polling of an identical fact does not multiply conflicts. Start with a bounded derivation for requested views and materialize a summary only if measurements justify it.
5. **Expose an optional integrity summary after API review.** Report the state and finding kinds next to the existing view, with a bounded number of response/index references on detail reads. Include coverage of the occurrence backfill so an incomplete history cannot appear clean. [Historical API design](HISTORICAL_API_DESIGN.md)

### Finding rules

| Finding | Classification |
| --- | --- |
| Identical observation or signer array reordered with the same membership and no other substantive difference | Preserve the occurrence. Treat identical facts as one comparison variant. Reordering by itself is informational. |
| Reported signer count differs from the array length, or signer indices repeat inside one row | Flag a field discrepancy separately. Preserve both values and leave the meaning for source investigation. The count mismatch is covered by a simulated test. [test/rpc.test.ts:46–58](https://github.com/omkar150p/phase-datahub/blob/13f36545f86cfe9c071f3da468c6920892a67341/test/rpc.test.ts#L46-L58) |
| Same class and hash in comparable context, different signer membership or reported counts | Record signer variation as an unresolved source finding. This is the live case. |
| Same certificate class, comparable view context, distinct non-null block hashes | Record unresolved hash variation. Distinct context should also be reported separately so signer indices are compared only where meaningful. No example of this hash case was found in the three analyzed captures. |
| Tentative followed by full for the same non-null hash and comparable context | Record a source-observed transition when response or wire ordering supports it. Keep evidence for both records. A full record followed by tentative is a separate out-of-order/regression observation. Distinct hashes or ambiguous ordering warrant a separate finding. [test/collector.integration.test.ts:88–122](https://github.com/omkar150p/phase-datahub/blob/13f36545f86cfe9c071f3da468c6920892a67341/test/collector.integration.test.ts#L88-L122) |

Use `unresolved` when a material discrepancy is established, including in a partial scan. Otherwise use `unknown` for unindexed or partial evidence, `no_discrepancy_observed` for a completed scan with no material variation, or `reported_transition` for an expected observed progression without an unresolved finding. An unresolved finding carries source evidence and can remain open even after the projection changes. The status conveys comparison results from the recorded source.

## Trade-offs and required tests

- An occurrence index removes repeated whole-response scans and makes individual evidence addressable. It adds up to one row per wire entry and another index write. Compare PostgreSQL relation growth, ingest transaction time and checkpoint lag on a full 10,000-entry page and on a representative soak.
- Real fixtures must produce 60 occurrence rows and respectively 58 and 56 projections. Assert disputed IDs and exact offsets, including the tied-timestamp example. Exercise identical duplicates, signer permutations, differing membership/counts, mismatched count and list, contexts, conflicting hashes, compatible and conflicting transitions, and out-of-order regressions.
- Assert lossless uint64 parsing, source isolation, retry and backfill idempotency, handling of empty and unsupported bodies, superseded polls, retention repairs, and rollback after an occurrence write fails. Re-run cursor, gap classification and projection compatibility tests.
