## Database migrations

`npm run db:migrate` executes one initialization SQL file inside a PostgreSQL transaction under an advisory lock. The schema uses `CREATE ... IF NOT EXISTS`, which is useful for new installations. Re-running the file on an existing database does not apply a new column or altered constraint to an existing table. The runner has no applied-version or checksum ledger. [package.json:9–16](https://github.com/omkar150p/phase-datahub/blob/13f36545f86cfe9c071f3da468c6920892a67341/package.json#L9-L16) · [src/migrate.ts:5–18](https://github.com/omkar150p/phase-datahub/blob/13f36545f86cfe9c071f3da468c6920892a67341/src/migrate.ts#L5-L18) · [src/database.ts:39–67](https://github.com/omkar150p/phase-datahub/blob/13f36545f86cfe9c071f3da468c6920892a67341/src/database.ts#L39-L67) · [db/001_init.sql](https://github.com/omkar150p/phase-datahub/blob/13f36545f86cfe9c071f3da468c6920892a67341/db/001_init.sql)

- Adopt a small ordered, append-only migration series and a `schema_migrations` ledger with version, name, SHA-256 and applied time. Continue using PostgreSQL transactions and the migration lock. A fresh DB replays the baseline and additive migrations. For existing DBs, check the relevant columns, constraints and indexes before recording the baseline. Fail with an actionable diagnostic on drift.
- Treat the released baseline as immutable and put observation tables and indexes into a separate migration. Keep the occurrence backfill outside the schema migration so callers are not blocked by a historical scan. Record backfill progress separately. Take a recoverable backup before upgrading a populated environment.
- Required tests are a clean install, upgrade from a populated copy of the current schema, re-run, concurrent migration attempts, drift and changed-checksum rejection, and DDL rollback. Compare stored raw bytes, view/read shape, gap references and checkpoints before and after upgrading. The existing tests create and tear down an isolated schema and currently exercise the initialization path. [test/collector.integration.test.ts:24–48](https://github.com/omkar150p/phase-datahub/blob/13f36545f86cfe9c071f3da468c6920892a67341/test/collector.integration.test.ts#L24-L48)

## API traffic controls and service health

The current API bounds the number of rows a caller can request. Request rate and database concurrency are separate controls. Collector-side concurrency, retries and timeouts apply to the upstream RPC. The API reads PostgreSQL through a pool and serves only the views route. Its general error handler currently returns a generic 500. [src/api.ts:17–32](https://github.com/omkar150p/phase-datahub/blob/13f36545f86cfe9c071f3da468c6920892a67341/src/api.ts#L17-L32) · [src/api.ts:93–112](https://github.com/omkar150p/phase-datahub/blob/13f36545f86cfe9c071f3da468c6920892a67341/src/api.ts#L93-L112) · [src/config.ts:19–36](https://github.com/omkar150p/phase-datahub/blob/13f36545f86cfe9c071f3da468c6920892a67341/src/config.ts#L19-L36) · [src/database.ts:32–37](https://github.com/omkar150p/phase-datahub/blob/13f36545f86cfe9c071f3da468c6920892a67341/src/database.ts#L32-L37)

| Area | Recommendation and trade-off | Required tests |
| --- | --- | --- |
| Rate limiting | Before exposing the API to external traffic, choose a bounded per-client request rate and a pooled DB connection budget from load measurements. A Fastify-compatible in-memory limiter is sufficient for one process. Use the ingress tier or a shared counter for an aggregate limit across replicas. Use `request.ip` with only the actual ingress proxies trusted. Preserve 429 and retry metadata through the central error handler. [Fastify rate-limit plugin](https://github.com/fastify/fastify-rate-limit) | Burst and reset behavior, per-client isolation, 429 and retry headers, forwarded-IP trust boundary, PostgreSQL pool saturation, and multiple instances if that topology is chosen. |

## CI and release evidence

Current CI uses pinned checkout/setup-node actions, Node 24, a PostgreSQL 17 service with a readiness check, read-only repository permissions and `npm ci` plus `npm test`. The published commit's GitHub Actions run passed. A fresh local run on Node 24.22.3 with PostgreSQL 17.12 passed all 30 tests. It verifies RPC fixtures, PostgreSQL behavior and the existing API contract. The minimum supported Node version is 22.12, and this workflow runs only Node 24. The live 24-hour soak and restore drill are still independent of CI. [Workflow](https://github.com/omkar150p/phase-datahub/blob/13f36545f86cfe9c071f3da468c6920892a67341/.github/workflows/tests.yml#L1-L41) · [Published CI run](https://github.com/omkar150p/phase-datahub/actions/runs/45880222377) · [Package scripts](https://github.com/omkar150p/phase-datahub/blob/13f36545f86cfe9c071f3da468c6920892a67341/package.json#L6-L16)

- Keep pull-request checks deterministic with saved fixtures and an ephemeral database. Add fresh/upgrade migration checks, the occurrence and pagination cases, and Node 22 coverage if it remains the supported floor. Pin the deployment runtime and database versions when provisioning them, and run a separate dependency advisory review. Keep cloud credentials and live-chain load out of pull-request CI.
- In an approved soak, capture starting and ending checkpoints, successful and failed polls, restart behavior, view and occurrence throughput, gaps by state, freshness, RPC rate-limit errors, growth of data/WAL and a small API read sample. Agree acceptable lag and growth before declaring readiness. Save the run conditions and explain any coverage gaps. A public GitHub repository is already available, and operating the API is a separate release decision.
