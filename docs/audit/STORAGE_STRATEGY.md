# Raw evidence storage strategy

Design for review. Baseline is published `main` at `13f36545f86cfe9c071f3da468c6920892a67341`.

## Baseline and sizing

The collector appends the submitted request text, the successful response body as `bytea`, the source, RPC method, purpose, receipt time and ingestion time. The bytes are the body read by the HTTP client after HTTP transfer/content decoding. Projection response references, gap evidence, retention-floor records and block head observations depend on the `rpc_responses` identity. The projection can be served through those metadata references without reading the body. Fixture checksums cover the repository captures. The live database currently has no SHA-256 column or external object catalog. ## Compressed archival

1. **Add an independent exporter.** Read committed rows in bounded, source-scoped batches. The collector continues to commit through its existing transaction. Keep an archive ledger keyed by the deployment's archive UUID and response ID. Work from committed rows with no verified ledger entry and rescan outstanding rows. PostgreSQL sequence values can have gaps and transactions can commit out of ID order, so an exporter high-water ID alone can miss evidence.
2. **Use a versioned gzip archive.** Start with a streamable JSONL pack. Preserve response body bytes as Base64, request text separately, and include response ID, chain/source identity, RPC method, purpose, receipt and ingestion times. Export PostgreSQL times losslessly, including precision beyond the JavaScript Date representation. Use numeric strings for identifiers. Record the format and producer version and measure a starting pack size in a soak. Response-per-object storage offers easier random reads at the cost of more objects and requests. Batching reduces request count and increases the work to retrieve one body. PostgreSQL remains the read path initially.
3. **Hash exact bytes.** Compute per-response SHA-256 over the stored `bytea`, and pack SHA-256 over the completed compressed bytes. Keep original byte length, row count, response IDs, compressed digest and a manifest that maps each response to its pack. Use a fixed codec format and deterministic serialization or retain the completed staged pack until the upload is verified. SHA-256 identifies captured content and detects later byte changes. Phase consensus validity is a separate question.
4. **Use a private Google Cloud Storage bucket.** Store each pack under a versioned prefix with archive UUID, source key, first/last ID and content digest. Use a private bucket with uniform bucket-level access and public access prevention. Authenticate with Application Default Credentials tied to the deployed workload identity. Grant object creation and the reads needed for verification at bucket scope, with a separate restore role and no routine delete grant. Keep the payload object as `application/gzip` without `Content-Encoding: gzip` so a normal read can verify the compressed bytes. Use CRC32C for the Cloud Storage transfer and SHA-256 for the application’s pack and records. [Cloud Storage checksums](https://cloud.google.com/storage/docs/data-validation) · [Cloud Storage transcoding](https://cloud.google.com/storage/docs/transcoding) · [Public access prevention](https://cloud.google.com/storage/docs/public-access-prevention) · [Application Default Credentials](https://cloud.google.com/docs/authentication/application-default-credentials)
5. **Make upload and verification retryable.** Upload with the create-only condition `ifGenerationMatch=0`. Read the exact generation back, verify the compressed digest and check each decoded body against its record digest and original length. Keep the manifest in the private bucket with the exact generation reference, then mark the response-to-pack mappings verified in the PostgreSQL ledger. On a precondition failure, verify the existing generation against the intended manifest before reusing it. If upload completes and the ledger update fails, a retry can reconnect the verified object to the pending rows. Expose export lag, unverified objects and mismatches as operator signals. [Cloud Storage request preconditions](https://cloud.google.com/storage/docs/request-preconditions)

## PostgreSQL retention policy

- **Initial policy.** Keep all existing raw bodies, response rows and evidence references in PostgreSQL. Keep normalized views, observations, gap history and checkpoints online. Add compressed copies in GCS and track verification separately. Retain evidence indefinitely for the initial release and measure the growth before setting any time-based tier.
- **Review after a restore drill.** Consider a shorter hot-body window only as a separate owner decision. A future cold tier would keep each response identity, digest and pinned archive pointer permanently available. Before removing a redundant inline copy, require independently recoverable verified copies, an audited restore drill and an explicit retention change. The archived evidence would remain retained. Apply no expiry rules to raw evidence objects during this plan.
- The current `response_body NOT NULL` rule and dependent foreign keys make direct row deletion a poor fit. A future body locator or separate payload relation would require an additive migration and a compatibility period. Early partitioning, cloud tier changes and permanent bucket retention locks can wait for measured volume and a reviewed retention decision. ## Recovery procedure

1. Restore a PostgreSQL backup or point-in-time snapshot into an isolated database, with the correct migration version. Preserve source/response identities, committed checkpoints, active and superseded gaps, and relationships to the raw responses.
2. Reconcile the restored archive ledger with reachable manifest generations. Pull any missing verified packs by exact generation. Verify the compressed SHA-256, unpack and verify each response digest, size and identity before rehydrating the body. Report missing objects, corrupt bytes or conflicting records and retain both sides for inspection.
3. Validate row counts, response and occurrence references, coverage and API samples. Resume collection from the committed checkpoint after the restore is checked. Retention may have advanced during the outage, so distinguish an upstream gap from a missing archive object.
4. Treat raw-object replay as an evidence recovery path. Exact reconstruction of checkpoint history, projection winners and gap supersession order requires the PostgreSQL backup or a verified transaction/order log in addition to the payloads. Set recovery time and recovery point objectives after measuring backup age, export lag and a rehearsal. ## Required tests

- Round-trip the public fixtures and the saved full window byte-for-byte. Include UTF-8, line endings, empty responses, uint64 fields, duplicate view occurrences and archive timestamps. Verify independent body and pack digests.
- Fault-inject failed upload, interrupted verification, a pre-existing object with the wrong digest, and process death between object creation and ledger commit. Assert idempotency and account for committed rows whose IDs arrive out of order. Keep PostgreSQL bodies available throughout.
- Restore into a clean database with one intentionally corrupted pack and one missing pack, then with verified data. Compare body hashes and API coverage to the baseline. Verify the cloud writer and consumer have only the intended scoped permissions, with retry and paging benchmarks at representative volume.
